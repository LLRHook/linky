# Linky growth research: September 17, 2026

Reviewed September 17, 2026. Research only: no competitor installations, comparative uptime tests, product changes, external posts, directory submissions or advertising purchases. Sources are current official documentation/repositories and individual public issue reports. Issue examples establish that someone experienced or requested something; they do not establish prevalence. Closed reports are historical design evidence, not claims that a competitor remains broken.

The proposed position is **a free hosted bot for ordinary social previews, concise English translations and useful YouTube details, with clear controls when delivery fails**. Reliability, privacy and speed advantages remain hypotheses until measured against comparable cases. Free hosting, open source and translation are already offered by competitors.

The [product roadmap](product-roadmap.md) tracks the seven planned priorities. This note supplies their evidence and the promotion rules checked on the review date.

## Scope and what Linky already ships

I first read the website's `research/competitive-roadmap.md` and the bot's `docs/optimization-directions-2026-09-15.md`. Both preserve older baselines; their proposals must not be mistaken for current gaps. I then checked the current README, delivery documentation and source at bot revision `27c849e8120e3cfe8ed529c84f5f80f0e447a8d1`.

Already shipped: private setup/channel selection and diagnosis; Reply/Replace; personal installation, `/fix` and context actions; per-platform switches; Original post and owner-only Remove; per-message bypass; reply synchronization; bounded Gateway-first checks and provider recovery; progress, retained Details and an operator delivery report; shared public Retry/Details/album controls; fair media scheduling and validated reuse; compact 300-character translated Instagram captions; YouTube display choices and private counts/comment replies. Do not propose these again as new work. [Current baseline](https://github.com/LLRHook/linky/tree/27c849e8120e3cfe8ed529c84f5f80f0e447a8d1), [delivery behavior](https://github.com/LLRHook/linky/blob/27c849e8120e3cfe8ed529c84f5f80f0e447a8d1/docs/delivery-reliability.md).

The release scope is seven hosted platforms: Instagram, TikTok, X/Twitter, YouTube, Bluesky, Reddit and Twitch clips, with the documented English translations and YouTube extras. Erome is disabled in every server using the hosted application; self-hosted operators can enable the supported media features on their own infrastructure. This document records the release decision, not independent proof of its deployment. Verify the restriction in the deployed bot before using it in a listing. Existing Erome engineering remains useful for self-hosters but is separate from hosted acquisition.

## Seven prioritized backlog candidates

All seven candidates have status **Planned**. None is a promise of a delivery date. All impact assessments below are hypotheses. Cost is relative engineering/operational effort: **S** isolated UI/configuration work, **M** multiple flows with persistence or network validation, **L** a new provider/parser and continuing maintenance. These are not delivery estimates. Preserve current source-deletion, ownership, byte, deadline and privacy guarantees throughout.

| Priority / candidate | Why new; impact and cost | Acceptance criteria before wider rollout |
| --- | --- | --- |
| **1. Repeatable ordinary-platform reliability corpus and a dated public status summary** | Existing diagnostics/reporting are shipped; scheduled semantic coverage, client spot checks and a published qualified summary are the addition. High trust/support potential; **M**, with ongoing fixture maintenance and bounded network cost. Motivated by GIF failures and FixEmbed's canary approach. | Cover text, video, GIF, gallery, unavailable and suppressed posts for advertised paths. Distinguish URL recognition, Discord metadata and actual client playback. Report sample size, date, platform, client, failures and latency; no production-p95 claim from small controlled samples. Test stale observations and upstream failure classification. Reuse the current report tool. |
| **2. Resolve mobile share URLs safely, starting with Instagram `/share/`** | A concrete missing URL form, not a new platform. Potentially high completion benefit; **M** plus redirect-provider maintenance. Evaluate Reddit app/short links next only after the first slice works. | Strict source/redirect allowlists, public-address checks at each hop, HTTPS only, fixed hop/time/byte caps, no cookies or arbitrary supplied endpoints. Normalize to a supported post before previewing. Tests cover mobile post/reel forms, loops, hostile destinations, removed/private posts and unchanged originals on failure. Validate live public examples separately. |
| **3. Persistent personal opt-out, then limited admin exclusions** | `!nolinky` already handles one message. A reversible per-server personal preference would avoid repeating it; role/category exclusions are a later slice if admins ask. **M**, high control/trust potential, small persistent-data cost. Competitor parity plus an inferred extension of intentional-bypass requests. | A member can privately enable/undo opt-out; automatic processing stops across supported platforms while deliberate manual actions retain their documented behavior. Define precedence with server settings and thread inheritance. Persist only necessary IDs/preferences, document deletion/retention, prevent admins silently overriding personal opt-out, and test edits/restarts/races. |
| **4. First-success setup check and visual mode examples** | `/setup`, channel pickers and `/diagnose` exist. Add a clearer saved-state/readiness summary and optional user-invoked test; avoid a separate dashboard. **S–M**, high activation hypothesis, low ongoing cost. | Show effective mode/channel and missing permissions after a save. Demonstrate Reply versus Replace and compact captions before selection. Any public test post requires an explicit test action. In a permissioned trial with willing admins, record completion time, wrong-channel attempts and assistance; fix observed confusion rather than declaring statistical success. |
| **5. A small presentation preset, preserving attribution and source links** | The fixed translated-Instagram excerpt is shipped. A supported compact/media-first choice is new; provider-controlled native captions cannot be promised the same limit. **M**, moderate clutter benefit and provider-mode maintenance. | Initially cover only a tested platform/provider mode. Show a faithful preview, preserve Original post/Remove ownership/media, handle captions unavailable and translations off, and retain useful failure text. Avoid arbitrary templates. Consider quiet notifications separately: mention suppression already exists and is not the same as suppressing all notification delivery. |
| **6. One opt-in target-language pilot** | English translation is shipped; a chosen non-English target and correct variants would be new. **M**, moderate/uncertain audience expansion with API quota and locale-testing cost. Competitor feature evidence is stronger than Linky-specific demand. | First obtain language preferences from willing existing admins. Pilot one requested locale, validate script variants, separate caches by target language, expose provider availability and quotas, retain source attribution, and preserve the preview when translation fails. Do not advertise image OCR, audio translation or every language. |
| **7. Evaluate YouTube community posts as the next content class** | Ordinary YouTube videos/counts are shipped; community posts are not. **M–L**, uncertain audience impact and ongoing parsing/provider cost. More concrete evidence than a generic request for dozens of new sites. | Evaluate public image/text examples, deleted/private posts and supported URL shapes. Preserve creator identity and source order; disclose unsupported variants. Require a bounded parser/transport and real client checks before enabling or advertising. If pilot admins do not use the feature, defer it rather than expanding the platform count for marketing. |

Defer a full dashboard, arbitrary user-supplied fixer endpoints, dozens of platforms, a new translation engine and expensive regional experimentation for hosted growth. They add maintenance or attack surface without evidence here that they improve activation. Keep self-host media optimization separate from the hosted acquisition backlog.

## Promotion gates and community rules

**Check Directory eligibility separately from the scope change.** Discord's September 9, 2026 App Discovery policy prohibits adult content in apps, and its inclusion guidance requires suitability for users 13+. The published policy states no owner-server exemption. Linky's release decision disables Erome throughout the hosted application. That does not, by itself, establish Directory eligibility, and no automatic ban based on a domain alone is inferred here. Check the deployed behavior and Discord's requirements before claiming eligibility. ## A small promotion experiment

1. **Prepare evidence before placement.** Create three short, dated demonstrations using owned or permitted non-adult examples: an ordinary social video, a translated Instagram/X caption with Original post, and YouTube counts/comment. Add one screenshot of private setup and one preserved-original failure/Retry example. Label metadata versus observed playback accurately and credit upstream services. No guaranteed-speed or most-reliable claim.
2. **Start with the existing site and an honest listing.** Refresh exact hosted/self-host scope, reuse the already-shipped account/server install paths, and prepare Top.gg reviewer steps. The concrete message can be: “Fix common social previews in Discord, keep control of originals, and read concise English captions and YouTube details.” This is proposed copy, not a verified performance claim.
3. **Seek a small permissioned pilot.** After approval, recruit a handful of willing admins through existing relationships or relevant recommendation threads that permit it. Disclose authorship. Ask which link failed, which setup step confused them and whether the result is too verbose. Do not copy private messages into public reports, seed competitor issues with advertisements or bulk-message servers.
4. **Measure the actual funnel before paying for clicks.** Site visits and invite clicks are not installs or first successful previews. Use the existing local delivery report and voluntary admin feedback first. The optional bot analytics adapter is separate; enabling it requires an explicit privacy/retention decision. Review the first complete week of hosted delivery telemetry before choosing a paid experiment, then review weekly. The identity-free archive cannot connect an invite to a server installation or establish returning-server cohorts. Use voluntary feedback for those missing steps, and report only measurements actually collected. Keep unavailable and failed samples in the record.
5. **Only then consider a capped paid test.** Choose one permitted listing placement or small sponsorship, a fixed approved spend and a dated stopping rule. Compare cost per activated trial server, not only impressions or votes; do not buy fake reviews. No placement price, conversion rate or return on spend was established here. Until activation is measured, prioritize helpful platform guides and real demonstrations over paid reach.

Search content should answer specific setup and failed-link questions with first-hand evidence. Google's current guidance favors useful original material and warns against producing many near-duplicate pages to manipulate AI/search results; there is no special guaranteed AI-recommendation shortcut. [Google guidance](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide).

## Weekly review after the first telemetry week

The existing seven-day Details history serves individual investigations. The new operator archive has a separate default of 30 days and 64 MiB and excludes Discord identities, content and URLs. Its report counts instrumented delivery attempts, with bounded stage timings and coverage/loss information. It does not measure every shared link, server activation, people reached or client playback. See the [operator reliability guide](https://github.com/LLRHook/linky/blob/main/docs/operator-reliability.md) for the implementation and report commands.

Start the review after the first complete week of hosted archive collection, then repeat weekly. Confirm collection dates, missing days and losses before interpreting results. Compare platform, path and outcome counts with the sample denominator and time window; distinguish zero observed attempts from missing coverage. Inspect stage timings and cache hits only where present. Keep low-volume groups visible with their sample sizes; do not present a small or selected sample as a production percentile or a success-rate comparison with competitors.

Use observed failure patterns and willing-admin feedback to select one bounded improvement from the planned priorities. Record the hypothesis, change, test cases and result; retain unsuccessful cases. Review support effort and whether the experiment produced useful previews before broadening it. No server-count, growth, conversion or latency target has been invented for this plan. A weekly review cadence is an operating proposal, not an installed automation or authorization to post externally.

## Limits of this assessment

This is a purposive sample of public reports, biased toward people who file issues. No surveys, competitor client tests, market-size estimates or comparative failure rates were collected. GitHub issue bodies and dates were also checked through the public GitHub API where page rendering omitted details. Competitor documentation can lag implementation, and closed issues can remain useful evidence without being current defects. Community rules and directory requirements must be checked again immediately before submission.
