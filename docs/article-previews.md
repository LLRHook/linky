# Public article previews

Post a public HTTPS article in a channel where Linky is enabled. In Replace mode, Linky credits the sender and removes the source only after Discord returns the complete prepared card and source/ownership checks pass. Reply mode keeps the source. Manual `/fix link:` and **Apps → Fix with Linky** keep it too.

The card normally contains a publisher-labelled headline, an excerpt of up to 300 characters, and a publisher image and publication date when available. MyAnimeList anime and manga entries use the same compact card with a synopsis and cover when available, labelled Source with Anime or Manga metadata. Text comes from the page's metadata, except for the labelled Telegraph and PDF cards below. Linky does not generate a summary, evaluate accuracy, translate the article, execute page scripts or bypass access restrictions.

## Supported pages and controls

- Articles need `og:type=article` or Schema.org `Article`, `NewsArticle` or `BlogPosting` JSON-LD in their HTML head, with a usable title. MyAnimeList anime and manga entry pages (`myanimelist.net/anime/<id>` or `/manga/<id>`, with an optional title slug) are also supported when the requested page, final page, canonical and `og:url` identify the same entry. Anime entries need `video.tv_show` or `video.movie` metadata; manga entries need `books.book`. Profiles, lists and entry subpages receive no catalogue exception. Apart from the Telegraph and PDF cards below, pages without article metadata remain unchanged, as do logins and private pages.
- Dated editorial links on `telegraph.co.uk` or `www.telegraph.co.uk` can still get a card when the publisher returns HTTP 402 with its specific TollBit bot-access refusal. Linky then searches Bing News's public RSS for the link's slug words on `telegraph.co.uk` and uses only an item whose link names exactly the same Telegraph host and article path. That card shows Bing News's headline, excerpt and thumbnail with **Publisher: The Telegraph** attribution and the footer **Headline via Bing News**; it has no publication time, because Bing's item time is its indexing time (seven hours before the publisher's time for the reported article). When Bing News has no matching item, fails or is slow, the title is made readable from the URL slug and labelled **Title from URL**, with **Site: The Telegraph** attribution and no excerpt, image or publication time. Neither card reads the article or confirms its availability. The requested and final article paths must match; lookalike hosts, invalid dates, unrelated redirects and other errors receive no card. Normal public metadata takes precedence when available.
- Public PDF files (served as `application/pdf`, or as `application/octet-stream` for a path ending in `.pdf`, and starting with a PDF header) get a card labelled **PDF document** with the host. Its title is the document's declared title (information dictionary or XMP), else the largest upright heading on the first page, else the file name; the footer says **Title from document metadata**, **Title from first page** or **Title from file name**. Placeholder titles such as `Untitled` or an editor's file name are ignored. The card adds the declared author, page count, file size and the document's creation time when available. Encrypted PDFs show only their page count and file name. Linky reads no further than the first page's text and does not render pages, summarize or check the content.
- Media pages keep Discord's native player. Pages declaring `og:video`, a `video.*`/`music.*` `og:type` or a Twitter player card are skipped even when they also carry Article JSON-LD (Tenor does). MyAnimeList anime entries are the one type exception: `video.tv_show` and `video.movie` are accepted only without declared video/player metadata. Discord's own domains and hosts it plays natively (Tenor, Giphy, Imgur, Streamable, Vimeo, Spotify, SoundCloud and similar) are never article candidates.
- Up to three distinct article or MyAnimeList entry links can share a message. All must be prepared before replacing it. Keep them separate from social and other links because authored cards can suppress Discord's native unfurls. Mixed messages retain the source and receive split-message guidance when supported.
- Keep unrelated website links separate too. When a message contains an article candidate without usable metadata or a supported fallback, automatic processing leaves the entire message unchanged, including any social links beside it.
- `/settings articles:false` or the setup Platforms menu disables article, PDF and MyAnimeList entry previews. Server enablement, channel scope, personal `/autofix` choices, `!nolinky`, hidden links, source-edit checks and owner-only Remove still apply. Original post and Details remain available to viewers.
- No API key is required. Operators using an explicit `REWRITE_PLATFORMS` list must add `articles`; an empty list enables available platforms. Social/provider and Erome URLs cannot fall back through articles to bypass their own settings.

## Truth Social posts

Truth Social serves the same placeholder metadata for every post, so Discord and the article reader see no post content. For public post links (`https://truthsocial.com/@user/ID` or `/@user/posts/ID`) Linky tries these signed-out public sources in order and uses the first that returns the requested post:

1. Truth Social's status API (`/api/v1/statuses/ID`): author name, handle and avatar, text, the first image or video poster, a **Play video** link to the post's MP4 on Truth Social, link-preview title, quoted text, ReTruth credit, reply/ReTruth/like counts and post time, for any public account. Truth Social's bot protection judges the client as well as the address: on October 26, 2026 the hosted bot's server received this API through Node's HTTPS client with Linky's user agent (21 of 21 requests), while curl, `fetch()` and bare user agents from the same server, and every Vercel region tested, received 403.
2. The operator's [Truth Social relay](truth-social-relay.md), when `TRUTH_SOCIAL_RELAY_URL` and `TRUTH_SOCIAL_RELAY_TOKEN` are set and the API refuses this host. The relay is a Cloudflare Worker, which Truth Social answered for every account tried; it returns the same status API response.
3. For `@realDonaldTrump`, the [Trump's Truth](https://www.trumpstruth.org) archive feed, which lists his latest 100 posts with text and archived media. Image posts show the image; video posts show the poster and a **Play video** link to the archived MP4. The footer credits the archive; counts and the avatar are unavailable. One feed request is cached for 30 seconds across lookups.
4. Truth Social's own post page metadata, which carries the full text of posts with text and the post's first image (Linky shows the original-size copy), plus the author's name from Truth Social's oEmbed endpoint. When the post has no image the page names the author's avatar instead. Truth Social renders that metadata only after a page has been visited once, so Linky revisits the page after 1.2 seconds when the first visit returns the placeholder. Videos are not in this metadata.

Discord's image proxy cannot fetch Truth Social's media hosts, so the bot downloads the post's first image (up to 8 MiB) and the author's avatar (up to 1 MiB) and uploads them with the card; Discord then shows them from its own CDN. Without the Attach Files permission, or beyond six uploads or 16 MiB in one message, the card links the original addresses, which Discord may not display. Additional images stay on Truth Social; the card says so. Private, direct, sensitive and content-warning posts, IDs that do not match the link, removed archive entries and responses that are not the expected type leave the original unchanged. Without the relay, a video-only post by another account, or one older than the archive feed, has no usable public source from a datacenter host and stays unchanged. Links inside post text show as `[link]`. Images and videos come only from Truth Social's `static-assets` hosts or the archive's storage. These cards follow the Articles setting and every rule above; all requests share the five-second limit and rate limits below.

## Request limits and privacy

Linky requests only public HTTPS pages, with no cookies or user credentials. DNS results must be public IPv4 addresses and the connection is pinned to a validated address while retaining normal TLS verification. Each redirect is checked again. Literal IPs, local hostnames, credentials, explicit ports, common account/API paths and known social-provider endpoints are rejected. Some otherwise public pages therefore remain unsupported.

Retrieval stops after the HTML head, 512 KiB or five seconds, with at most three redirects. For a blocked Telegraph link Linky reads only the refusal response, up to 4 KiB, then makes one Bing News RSS request to `www.bing.com` under the same public-DNS, pinning and 512 KiB limits; it must finish 250 ms before the five-second deadline, or the URL-title card is used. PDFs are read to at most a 4 MiB prefix within the same deadline; larger files keep their declared size. The PDF reader is dependency-free and bounded: Flate streams only, 4 MiB per stream and 24 MiB per file after inflation, a shared token budget, limited nesting and first-page operators. Larger unlinearized PDFs whose first page lies beyond the prefix fall back to the file name. Compressed responses that ignore the identity request are skipped. A process allows four active lookups and 30 new lookups per minute; it does not queue an unlimited backlog. Those limits are shared across servers. Successful metadata, Bing News headlines and PDF cards are cached in memory for five minutes, misses and Telegraph URL-title cards for 15 seconds, with at most 100 entries. URLs and metadata are not written to the delivery archive. Cache contents disappear on restart.

The publisher sees a request from the bot host; for a blocked Telegraph link Bing also receives the link's slug words as a search query. Bing's RSS terms describe personal, non-commercial use in an RSS aggregator; operators running Linky commercially should review them. Discord retrieves the optional public image separately; source changes or Discord's image proxy can still make that image unavailable. A confirmed card proves that Discord returned the prepared fields, not that the article is accurate or an image rendered on every device. Missing usable metadata leaves the original unless a supported Telegraph or PDF card can be prepared; manual requests explain unsupported pages.

The initial requested example is the Manhattan Institute's *The Fiscal Impact of Immigration (2025 Update)*. Article support is based on metadata format, with PDF document cards and separate host-specific exceptions for MyAnimeList catalogue entries and blocked Telegraph editorial links. The reported examples are The Telegraph's *China rejects Mbappe and Real Madrid apologies over ‘outrageous’ Mao joke* and KITP's *Proof by OpenAI of the Existence of Quantum Yang-Mills theory* PDF.
